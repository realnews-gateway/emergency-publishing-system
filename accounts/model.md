# Account Data Model

This document defines the data model for the system‑wide anonymous
account layer. The model is intentionally minimal, privacy‑preserving,
and fully isolated from all transport, routing, and Emergency Channel
processing.

The account model supports pseudonym identity, personal content
management, cross‑application favorites, and optional recovery features.

---

## 1. Account Identifier

Each account is assigned a stable, opaque identifier.

Fields:

- account_id — Internal opaque identifier (non‑guessable, non‑sequential)
- created_at — Account creation timestamp
- updated_at — Last modification timestamp

Properties:

- Cannot be derived from user behavior or metadata
- Never exposed to the Emergency Channel
- Never embedded in published content
- Not linked to IP, device, or session data

---

## 2. Authentication Fields

Authentication is minimal and optional.

Fields:

- password_hash — Stored using modern, memory‑hard hashing
- email (optional) — For password recovery only
- email_verified — Boolean
- two_factor_secret (optional) — Time‑based 2FA secret
- two_factor_enabled — Boolean

Properties:

- Email is optional and never required
- No phone numbers or personal identifiers are stored
- 2FA is optional and never required
- No login metadata (IP, device, region) is stored

---

## 3. Pseudonym Identity

Each account receives a persistent pseudonym used across applications.

Fields:

- pseudonym_name — System‑generated display name
- pseudonym_avatar — System‑generated avatar descriptor
- pseudonym_version — Incremented when pseudonym is regenerated

Properties:

- Pseudonym is public‑facing but cannot be reversed to account_id
- Applications display pseudonym, not account identifiers
- Pseudonym may be regenerated by the user

---

## 4. Personal Content Index

Applications may store references to content created by the account.

Fields:

- posts — Array of application‑defined content references
- last_activity_at — Timestamp of last content interaction

Properties:

- Stored per account, not globally indexed
- Applications define the schema of each content reference
- Never exposed to the Emergency Channel

---

## 5. Favorites (Cross‑Application)

The account layer provides a unified favorites system.

Fields:

- favorites — Array of objects:
  - app_id — Application identifier
  - item_id — Application‑defined content identifier
  - added_at — Timestamp

Properties:

- Favorites are private to the user
- Applications define what can be favorited
- Emergency Channel never receives favorites data

---

## 6. Security Flags

Internal fields used to protect the account.

Fields:

- compromised_flag — Indicates suspected credential compromise
- recovery_required — Forces password reset on next login
- lockout_until — Timestamp for temporary lockout

Properties:

- No behavioral analytics or profiling
- No IP‑based or device‑based security logic
- Flags are internal and never exposed to applications

---

## 7. Data Isolation Guarantees

The account model enforces strict isolation:

- No IP addresses stored
- No device identifiers stored
- No transport metadata stored
- No session history stored
- No behavioral logs stored
- No cross‑application tracking beyond favorites and posts
- No linkage to Emergency Channel content

All fields are designed to prevent identity correlation across sessions,
applications, or network environments.

---

## 8. Application Integration

Applications interact with the account layer through:

- Authentication (optional)
- Pseudonym retrieval
- Personal content listing
- Favorites management

Applications **must not**:

- Store account identifiers in published content
- Send account identifiers to the Emergency Channel
- Infer identity from pseudonyms
- Store transport metadata

---

The account model provides a minimal, privacy‑preserving foundation for
identity across the Empus ecosystem while maintaining strict separation
from all transport and processing layers.
